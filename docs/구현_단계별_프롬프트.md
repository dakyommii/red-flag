# 부동산 사기 추리·검증 게임 — 단계별 구현 프롬프트

이 문서는 `부동산_사기_추리게임_MVP_설계문서.md`(이하 "설계문서")를 실제로 구현하기 위해,
AI 코딩 에이전트(Claude Code 등)에게 **순서대로 그대로 붙여넣어 사용할 수 있는 프롬프트 모음**이다.

## 사용 방법

1. Phase는 반드시 순서대로 진행한다. 각 Phase는 이전 Phase의 산출물(코드, 데이터 파일)을 전제로 한다.
2. 각 프롬프트 하단의 **완료 조건**을 통과해야 다음 Phase로 넘어간다. 완료 조건은 사람이 직접 확인하거나,
   에이전트에게 "완료 조건을 스스로 점검하고 리포트하라"고 지시해도 된다.
3. 프롬프트 안의 `설계문서 N장`은 `부동산_사기_추리게임_MVP_설계문서.md`의 해당 장을 가리킨다.
   에이전트가 실행 중 해당 문서를 참조하도록 프롬프트에 파일 경로를 명시해 두었다.
4. 설계문서 22장의 원칙 — **"게임의 정답(Risk Pattern, Evidence, Contradiction, Ending Condition)은
   LLM이 아니라 `case.json`에 명시한다. LLM은 NPC 발화, 자유발화 평가, 피드백 생성에만 사용한다"** —
   은 모든 Phase에서 반복적으로 강조된다. 이 원칙이 코드에 반영되지 않으면 즉시 되돌아가 수정한다.
5. MVP 필수 구현(Phase 0~7)을 먼저 끝내고, 이후 2차 구현(Phase 8~11)으로 확장한다. (설계문서 20장 기준)

## Phase 0 — 프로젝트 스캐폴딩

```text
설계문서(부동산_사기_추리게임_MVP_설계문서.md) 16장(백엔드 아키텍처), 18장(프론트엔드 구조)을 참고하여
프로젝트 초기 구조를 세팅해줘.

요구사항:
- 백엔드: FastAPI 기반. 디렉토리는 backend/ 하위에 두고, 다음 모듈을 빈 껍데기(라우터/서비스 스텁)로 생성한다.
  - case_engine (CASE 로딩/상태 관리)
  - investigation_engine (조사 처리)
  - evidence_engine (증거 등록)
  - npc_service (LLM 연동, 지금은 스텁)
  - evaluator_service (LLM 연동, 지금은 스텁)
  - report_generator (LLM 연동, 지금은 스텁)
  - game dataset을 담을 data/cases/ 디렉토리
- 프론트엔드: React/Next.js. frontend/ 하위에 설계문서 18장의 화면 구조를 그대로 반영한
  라우트/컴포넌트 스켈레톤을 만든다.
  (CaseSelect, CaseBriefing, Investigation{DocumentViewer, EvidenceBoard, NPCChat}, FinalDecision, CaseReport)
- 세션 상태를 저장할 저장소는 MVP 단계이므로 인메모리 딕셔너리로 시작한다(추후 DB로 교체 가능하도록
  session store를 인터페이스로 분리).
- .env.example에 LLM API 키 플레이스홀더를 추가한다.
- README에 로컬 실행 방법(백엔드/프론트엔드 각각)을 작성한다.

이 단계에서는 게임 로직을 구현하지 않는다. 오직 실행 가능한 뼈대만 만든다.
```

**완료 조건**
- `uvicorn` 또는 동일한 방식으로 백엔드가 기동되고 `/health` 같은 헬스체크 엔드포인트가 200을 반환한다.
- 프론트엔드 dev 서버가 기동되고 빈 페이지 라우트들이 404 없이 열린다.
- 게임 판정 로직, CASE 데이터가 전혀 없는 순수 스캐폴딩 상태다.

## Phase 1 — Case Engine (정적 CASE 1개로 전체 흐름 동작)

```text
설계문서 15.1절(Case 데이터 구조), 17장(API 설계 중 CASE 시작 API), 21장 Phase 1을 참고하여
Case Engine을 구현해줘.

요구사항:
- data/cases/trust_property_case.json 파일을 만든다. 설계문서 10장 "CASE 3 — 신탁부동산" 시나리오를
  기반으로, 15.1절의 스키마(case_id, title, domain, difficulty, scenario, hidden_truth,
  investigations, npc_personas, contradictions, safe_actions, ending_conditions, source)를 채운다.
  이 시점에서는 investigations/npc_personas/contradictions는 빈 배열이어도 된다(다음 Phase에서 채움).
- POST /api/cases/{case_id}/start 를 구현한다.
  - case.json을 로드하고 session_id를 발급, 세션 상태(session store)에 저장한다.
  - 응답으로 CASE 브리핑에 필요한 정보(설계문서 3.1절 화면 스펙)를 반환한다.
- GET /api/cases 로 선택 가능한 CASE 목록(case_id, title, difficulty)을 반환한다.
- 프론트엔드 CaseSelect, CaseBriefing 화면을 이 API와 연결한다. 브리핑 화면은 설계문서 3.1절의
  예시 포맷(CASE 번호, 난이도, 계약 종류, 매물 정보, 목표, 조사 포인트)을 그대로 렌더링한다.

주의: 이 Phase에서는 hidden_truth(fraud_type, risk_patterns)를 절대 프론트엔드로 노출하지 않는다.
정답 데이터는 서버에만 존재해야 한다.
```

**완료 조건**
- CASE 목록 조회 → CASE 시작 → 브리핑 화면 표시까지 end-to-end로 동작한다.
- `case.json` 하나만으로 위 흐름이 데이터 하드코딩 없이 동작한다(새 CASE 파일을 추가하면 그대로 동작해야 함).
- 세션 응답에 `hidden_truth` 필드가 포함되지 않는다.

## Phase 2 — Investigation & Evidence Engine

```text
설계문서 4장(조사 시스템), 5장(증거 시스템), 15.2절(Investigation 데이터 구조),
17장(조사/증거 등록 API)을 참고하여 Investigation Engine과 Evidence Engine을 구현해줘.

요구사항:
- Phase 1의 trust_property_case.json에 설계문서 10장 "CASE 3" 기준으로 investigations 배열을 채운다.
  최소한 "등기 정보", "중개사 정보", "계약서" 조사 항목을 포함하고, 각 항목은
  15.2절 스키마(investigation_id, name, cost, time_cost, unlock_condition, document_id)를 따른다.
  각 문서의 실제 내용(document_id가 가리키는 텍스트)도 CASE 데이터에 추가한다. 신탁 관련 문구가
  등기 정보 문서 안에 포함되어야 한다(설계문서 7장 모순 발견 예시와 연결됨).
- POST /api/game/{session_id}/investigate 를 구현한다.
  - investigation_id를 받아 cost/time_cost를 세션의 남은 포인트/시간에서 차감한다.
  - 포인트/시간이 부족하면 명확한 에러를 반환한다.
  - 해당 문서 내용을 응답으로 반환한다.
- POST /api/game/{session_id}/evidence 를 구현한다.
  - 플레이어가 문서의 특정 부분을 증거로 등록하면, 서버가 해당 문서/부분이 CASE 데이터의 어떤
    Evidence 패턴과 매칭되는지 rule-based로 판정한다(설계문서 5.1절 Evidence 데이터 구조 참고).
  - 매칭에 성공하면 세션의 Evidence Board에 등록하고 evidence_id를 반환한다.
  - 매칭 판정은 LLM이 아니라 CASE 데이터에 정의된 규칙으로 수행한다(설계문서 22장 원칙).
- 프론트엔드 Investigation 화면(DocumentViewer, EvidenceBoard)을 구현한다. 설계문서 18장의
  레이아웃 예시(조사 메뉴 / 문서·NPC / Evidence Board 3분할)를 따른다.

이 Phase에서는 아직 NPC 대화, 모순 지적, 최종 판단은 구현하지 않는다.
```

**완료 조건**
- 조사 포인트가 부족한 상태에서 조사를 시도하면 서버가 거부한다.
- 등기 정보 문서에서 신탁 관련 부분을 증거로 등록하면 `TRUST_REGISTRATION` Evidence가 생성된다.
- Evidence Board에 등록된 증거가 프론트엔드에 즉시 반영된다.

## Phase 3 — NPC 대화 (LLM 연동)

```text
설계문서 8장(NPC 대화 시스템), 9장(플레이어 질문 처리), 17장(NPC 질문 API)을 참고하여
LLM 기반 NPC를 구현해줘.

요구사항:
- trust_property_case.json에 npc_personas 배열을 채운다(설계문서 8.2절 스키마: npc_id, role,
  case_id, knowledge, strategies, pressure_level, hidden_information).
  CASE 3의 중개사 NPC를 최소 1명 정의하고, hidden_information에는 "계약 권한 이슈"를 넣는다.
- NPC System Prompt를 설계문서 8.3절 개념을 바탕으로 구성한다. 반드시 다음을 포함한다:
  - CASE에 정의된 사실(knowledge, hidden_information)만 사용하고 새로운 사실을 창작하지 않는다.
  - 정해진 persuasion strategy(설계문서 8.2절 strategies) 범위 안에서만 압박/설득한다.
  - fraud_type이나 정답을 직접 말하지 않는다.
- POST /api/game/{session_id}/chat 을 구현한다.
  - npc_id, message, 대화 히스토리를 받아 (Case Context + Persona + History)를 LLM에 전달하고
    NPC 응답을 반환한다(설계문서 9장 구조 그대로).
  - 대화 히스토리는 세션 상태에 저장한다.
- 프론트엔드 NPCChat 컴포넌트를 구현한다. 자유 텍스트 입력과 대화 로그를 표시한다.
- LLM 응답이 CASE에 없는 사실을 생성하는지(hallucination) 확인할 수 있도록, 개발 환경에서는
  프롬프트와 응답을 로그로 남긴다.

주의: NPC가 정답(신탁 문제 등)을 직접 알려주면 실패다. hidden_information은 플레이어가 스스로
조사로 발견해야 하는 정보이며, NPC는 질문을 받았을 때 회피/모호한 태도(설계문서 8.2절 strategies)로
반응해야 한다.
```

**완료 조건**
- "집주인이 직접 계약하면 문제없나요?" 같은 질문에 NPC가 설계문서 7장 예시처럼
  "집주인이 직접 계약하면 아무 문제 없습니다" 류의 안전 주장(SAFETY_CLAIM)으로 응답한다.
- NPC가 hidden_information(계약 권한 이슈)을 스스로 먼저 밝히지 않는다.
- 동일 세션에서 대화 히스토리가 유지된다.

## Phase 4 — 모순 발견 + 최종 판단 + 점수 (Rule 기반)

```text
설계문서 7장(모순 발견 시스템), 12장(최종 판단 시스템), 15.3절(Contradiction 구조),
17장(모순 제출/최종 판단 API)을 참고하여 판정 로직을 구현해줘.

요구사항:
- trust_property_case.json에 contradictions 배열을 채운다(15.3절 스키마: contradiction_id, left,
  right, score). left/right는 각각 NPC 발언 id와 Evidence id를 가리킨다.
  Phase 3의 NPC 발언("집주인이 직접 계약하면 문제없다")과 Phase 2의 Evidence(신탁 등기 정보)를
  연결하는 모순을 최소 1개 정의한다.
- POST /api/game/{session_id}/contradiction 을 구현한다.
  - 플레이어가 (NPC 발언, Evidence) 쌍을 제출하면, CASE 데이터의 contradictions와 rule-based로
    매칭한다. 일치하면 CONTRADICTION FOUND를 반환하고 점수를 가산한다.
- POST /api/game/{session_id}/decision 을 구현한다.
  - 플레이어의 최종 선택(SAFE_TO_PROCEED / NEED_MORE_VERIFICATION / STOP_CONTRACT)을 받는다.
- 점수 계산 로직을 구현한다(설계문서 12장 배점표를 그대로 반영):
  - 핵심 위험 신호 발견 40, 중요 증거 확보 20, 모순 발견 15, 효율적 조사 10, 최종 판단 15 (총 100).
  - "핵심 위험 신호 발견"은 세션에 등록된 Evidence의 pattern이 hidden_truth.risk_patterns와
    얼마나 겹치는지로 계산한다.
  - "최종 판단" 점수는 단순 정답 일치가 아니라, ending_conditions(다음 Phase에서 CASE에 정의)에
    따라 계산되도록 인터페이스를 열어둔다.
- 프론트엔드에 모순 연결 UI 최소 버전(NPC 발언 목록 ↔ Evidence 목록에서 하나씩 선택 후 제출)과
  FinalDecision 화면(3지선다)을 구현한다.

이 Phase의 모든 판정은 LLM 없이 CASE 데이터 + Rule로만 이루어져야 한다(설계문서 22장 원칙).
```

**완료 조건**
- 올바른 (NPC 발언, Evidence) 쌍을 제출하면 CONTRADICTION FOUND가 반환되고, 틀린 쌍은 거부된다.
- 최종 판단 제출 후 100점 만점 기준 점수가 계산되어 반환된다.
- 동일한 요청을 반복 제출해도 점수가 중복 가산되지 않는다.

## Phase 5 — AI Evaluator (자유발화 의미 평가)

```text
설계문서 14장 "AI 3 — 사용자 발화 평가", 9장을 참고하여 Evaluator Service를 구현해줘.

요구사항:
- 플레이어가 NPCChat이나 별도 입력창에 자유 문장(예: "일단 계약하지 말고 등기부터 확인할게요")을
  입력했을 때, 이를 LLM으로 분류하여 설계문서 14장 예시 형태의 구조화된 결과를 반환한다.

  {
    "matched_actions": ["STOP_TEMPORARILY", "CHECK_REGISTRY"],
    "risk_level": "SAFE"
  }

- matched_actions의 후보 값 목록은 CASE 데이터(safe_actions, 15.1절)에 정의된 값으로 제한하고,
  LLM 출력을 이 화이트리스트에 대해 검증(validation)한다. 화이트리스트에 없는 값이 나오면
  버리거나 재시도한다 — LLM이 임의의 새로운 액션을 만들어내지 못하게 막는다.
- 이 평가 결과를 세션 상태에 누적하여, Phase 4의 "최종 판단" 점수 계산에 반영할 수 있게 한다
  (예: STOP_TEMPORARILY, CHECK_REGISTRY 같은 안전 행동을 조기에 언급하면 가점).
- 실패/애매한 응답에 대한 폴백을 정의한다(예: 분류 실패 시 risk_level "UNKNOWN"으로 저장하고
  점수에는 반영하지 않음).

주의: Evaluator는 "정답을 매기는" 것이 아니라 "플레이어 발화가 CASE에 정의된 안전 행동 중
무엇에 해당하는지 분류"하는 역할까지만 한다. 정답 여부 판단 자체는 CASE 데이터가 갖는다.
```

**완료 조건**
- 화이트리스트에 없는 액션이 LLM 출력에 섞여도 서버 응답에는 노출되지 않는다.
- "등기부터 확인할게요" 같은 문장이 CHECK_REGISTRY로 분류되는 것을 수동 테스트로 확인한다.
- 분류 실패 케이스가 게임을 중단시키지 않고 안전하게 처리된다.

## Phase 6 — CASE REPORT (개인화 피드백)

```text
설계문서 13장(CASE REPORT), 14장 "AI 4 — 개인화 피드백"을 참고하여 Report Generator를 구현해줘.

요구사항:
- GET /api/game/{session_id}/report 를 구현한다.
- Rule 기반으로 다음을 세션 상태에서 계산한다(LLM 아님):
  - 최종 판단, 등급(점수 구간별 A/B/C 등)
  - 발견한 위험 신호 vs hidden_truth.risk_patterns 대비 놓친 위험 신호
  - 행동 Timeline(조사/질문/증거등록/판단 각 액션에 타임스탬프를 기록해두었다가 그대로 나열)
- LLM은 위 구조화된 데이터를 입력받아 "개인화된 코멘트"만 생성한다(설계문서 14장 AI 4).
  코멘트가 사실관계(위험 신호, 점수 등)를 새로 만들어내지 않도록, 프롬프트에 구조화된 데이터를
  명시적으로 주입하고 "아래 데이터에 없는 사실은 언급하지 말라"는 제약을 건다.
- CASE의 source(15.1절 source.case_ids, official_sources)가 있으면 "이 CASE는 실제 발생한
  전세사기 유형을 교육 목적으로 재구성한 시나리오입니다" 문구와 공식 출처 URL을 함께 표시한다.
- 프론트엔드 CaseReport 화면을 설계문서 13장 예시 포맷대로 구현한다.

이 Phase를 끝내면 설계문서 20장 "반드시 구현" 목록(MVP 필수 구현)이 전부 완료된 상태가 된다.
```

**완료 조건**
- CASE 완료 후 리포트 화면에 등급, 발견/놓친 위험 신호, Timeline, 개인화 코멘트, 실제 사례 문구가
  모두 표시된다.
- 리포트의 위험 신호/점수/Timeline 수치가 LLM 호출 없이도 (코멘트 텍스트만 없이) 동일하게 재현된다
  — 즉 사실 데이터는 rule-based로 결정론적이다.

## Phase 7 — CASE 확장 (CASE 1, 2, 4, 5, FINAL CASE)

```text
설계문서 10장(CASE 1~5), 11장(FINAL CASE)을 참고하여, Phase 1~6에서 만든 엔진이 CASE 데이터만
추가하면 그대로 재사용되는지 검증하면서 나머지 CASE들을 데이터로 추가해줘.

요구사항 (CASE별로 data/cases/*.json 신규 생성, 엔진 코드는 원칙적으로 수정하지 않는다):
1. CASE 1 — 높은 전세가율 (난이도 ★☆☆☆☆): risk_patterns = HIGH_JEONSE_RATIO, URGENCY
2. CASE 2 — 최근 소유권 변경 (★★☆☆☆): RECENT_OWNERSHIP_CHANGE, MULTIPLE_PROPERTY_ACQUISITION,
   HIGH_JEONSE_RATIO
3. CASE 4 — 청약/분양 사칭 (★★★★☆): FAKE_AUTHORITY, FAKE_WEBSITE, URGENCY, PAYMENT_PRESSURE.
   조사 항목에 "문자", "사이트", "분양공고", "청약Home", "건설사 공식 연락처", "입금계좌"를 포함하고,
   핵심 학습 포인트("상대가 제공한 검증 수단만으로 상대를 검증하지 않는다")가 investigation
   unlock_condition 설계에 드러나게 한다.
4. CASE 5 — 분양 투자 (★★★★☆): 모든 위험 신호가 곧바로 사기를 의미하지 않도록 설계한다
   (설계문서 10장 CASE 5 "특징" 참고). safe_actions와 ending_conditions에 "계약 진행 가능"이
   최고점이 되는 케이스도 만들어, 최종 판단 점수 로직이 STOP_CONTRACT에 편향되지 않는지 검증한다.
5. FINAL CASE — 가족의 계약을 막아라 (설계문서 11장): 제한시간 20:00을 사용한다(Phase 9에서
   구현할 제한시간 시스템이 아직 없다면, 이 Phase에서는 프론트 카운트다운 UI만 우선 붙이고
   서버 강제 종료 로직은 Phase 9로 미룬다). ending_conditions에서 최고점 답변이 "사기다"가 아니라
   "오늘 계약하지 말고 추가 확인한다"류의 판단이 되도록 배점을 설계한다(설계문서 11장 "핵심" 참고).

각 CASE 추가 후, 엔진 코드 변경 없이 동작하는지 회귀 테스트한다. 만약 엔진 수정이 꼭 필요하다면
그 이유를 명시하고 최소한으로 수정한다.
```

**완료 조건**
- 6개 CASE(1~5, FINAL) 모두 CaseSelect에서 선택 가능하고 각각 처음부터 끝까지(조사→증거→대화→
  모순→판단→리포트) 완주 가능하다.
- CASE 5에서 "계약 진행 가능"을 선택해도 상황에 따라 고득점이 나올 수 있음을 확인한다(사기
  여부 이분법이 아님을 검증).
- 새 CASE 추가가 데이터 파일 작성만으로 가능했는지 확인한다(엔진 로직 변경 최소화 여부 기록).

## 2차 구현 (설계문서 20장 "2차 구현" 대응)

MVP 필수 구현(Phase 0~7)이 끝난 뒤 진행한다.

### Phase 8 — 모순 연결 UI 고도화

```text
Phase 4에서 만든 최소 모순 연결 UI를 설계문서 7장 예시(NPC 발언 ↕ 문서 Evidence를 드래그 또는
클릭으로 연결)에 가깝게 개선해줘. 정답 매칭 로직은 이미 Phase 4에서 구현된 rule을 그대로 재사용하고,
UI/UX만 개선한다(연결선 시각화, 오답 시 피드백, 이미 시도한 조합 재제출 방지 등).
```

### Phase 9 — 제한시간 모드

```text
설계문서 4.2절(제한시간 모드), 11장(FINAL CASE 제한시간)을 참고하여 제한시간 시스템을 구현해줘.

요구사항:
- CASE 데이터에 time_limit_seconds(선택 필드)를 추가하고, 있는 경우 세션 시작 시 타이머를 건다.
- 조사할 때마다 investigation의 time_cost만큼 서버 측 남은 시간을 차감한다(클라이언트 타이머는
  표시용이며 서버가 최종 판정 소스여야 한다).
- 시간이 0이 되면 서버가 세션을 자동으로 "시간 초과" 상태로 전환하고, 남은 조사 없이 바로
  최종 판단을 강제하거나 감점 처리한다(설계문서 11장 FINAL CASE 배점 의도를 참고해 정책 결정).
- 프론트엔드에 카운트다운 UI(설계문서 3.1, 11장 예시의 "계약까지 남은 시간")를 붙인다.
```

### Phase 10 — 조사 포인트 & Unlock 시스템 강화

```text
설계문서 4.1절(조사 포인트 표), 3.2절("특정 단서를 발견하면 새로운 조사 항목을 unlock")을
참고하여 조사 시스템을 강화해줘.

요구사항:
- investigation.unlock_condition(15.2절 스키마에 이미 있는 필드)을 실제로 평가하는 로직을
  구현한다. 조건은 "특정 Evidence 등록됨" 또는 "특정 조사 완료됨" 같은 형태로 CASE 데이터에
  선언적으로 표현하고, 엔진은 이를 해석만 한다(하드코딩 금지).
- 초기 미노출 조사 항목이 잠긴 상태(lock 아이콘 등)로 보이거나 아예 목록에서 숨겨지도록
  프론트엔드를 조정한다(CASE별로 선택 가능하게 설정 필드 추가).
- CASE 3, FINAL CASE 등 기존 CASE 중 최소 1개에 실제로 unlock 체인을 추가해 동작을 검증한다.
```

### Phase 11 — AI CASE 자동 생성 (Case Generator)

```text
설계문서 14장 "AI 1 — 실제 사건 → CASE 생성", 19장(데이터 파이프라인 연결)을 참고하여
Case Generator를 구현해줘.

요구사항:
- 입력: real_cases.json(실제 사례, 개인정보 제거됨), fraud_taxonomy(위험 신호 정의),
  official knowledge(공식 예방정보) — 설계문서 19장 파이프라인을 참고해 detect-voicephsing
  프로젝트에서 재사용 가능한 데이터가 있는지 먼저 확인한다.
- LLM Case Generator는 위 입력을 context로만 사용하고, 15.1절 스키마를 따르는 case.json 초안을
  생성한다. 생성 시 "실제 사례와 공식 Knowledge에 없는 법률/사실을 임의로 만들지 말 것"을
  명시적으로 제약한다(설계문서 14장 AI 1 원칙).
- 생성된 case.json은 자동으로 게임에 반영되지 않고, 검증 단계(사람 검토 또는 스키마/일관성
  자동 검증)를 반드시 거치도록 파이프라인을 구성한다(설계문서 14장의 "검증" 단계).
- 최소 1개의 새 CASE를 이 파이프라인으로 생성해보고, Phase 7의 완료 조건과 동일한 기준으로
  엔진 수정 없이 플레이 가능한지 확인한다.
```
